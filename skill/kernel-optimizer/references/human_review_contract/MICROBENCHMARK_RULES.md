# Microbenchmark 进入人工报告的规则

## 六字段摘要

每个进入主页面的实验必须用中文回答六个字段：

1. **问题**：它只回答哪个因果问题。
2. **保持不变**：与生产相同且在对照间冻结的条件。
3. **唯一改变**：唯一操纵变量；若不止一个，必须拆实验或降级证据。
4. **结果**：原始 A/B 数字、单位、统计量和重复方式。
5. **含义**：从结果可以推出的微架构结论。
6. **边界**：不可推广到哪些几何、cache、所有权或资源结论。

缺少任一字段时，实验只能留在开发者证据层，不能进入主报告。

## 精确性门禁

报告引用的 microbenchmark 必须经过：

- 计时器零工作控制、timer resolution 和 kernel-count 检查；
- 最终二进制中的目标指令与控制流核验；
- live sink、DCE 负/正控制及正确性检查；
- warm/cold cache、clock/power/thermal 和竞争负载记录；
- 原始样本、稳健统计、交错 AB/BA 和独立进程复验；
- 几何、寄存器、shared、布局、地址、ABI、数值边界匹配；
- 预注册的单调性、机制和跨层预测门禁。

样本多不能弥补机制错误。Profiler 采样不与用于接受决策的计时分布混用。

## 构造服务面而不是单点

延迟、吞吐和“无法打满”的证明至少按问题选择扫描：

- grid/CTA 数与 CTA waves；
- 每 CTA payload/计算量；
- 独立请求或 accumulator 数；
- warp 数、角色宽度和 producer/consumer 比例；
- 由寄存器/shared 控制的驻留数；
- cache warm/cold 与工作集大小；
- transaction、对齐、stride 和地址聚合模式；
- A-only、B-only、A+B 串行、A+B 重叠；
- barrier 到达偏斜与无偏斜控制。

曲线必须同时标出生产工作点和匹配饱和点。若曲线尚不完整，只能陈述
已观察方向，不能宣布“带宽/计算已饱和”或“无法打满”。

## 延迟与吞吐实验不能混用

- 依赖链测量单条链的首次/相关指令延迟。
- 多独立链测量稳态 issue/service 吞吐。
- `repeat=1` 与高 repeat 斜率分开报告。
- checksum、地址计算、barrier、sink 的污染单独量化。
- cache 边界不明时使用“请求服务率”，不用 HBM/L2 带宽名称。

## 自动积累

报告暴露出的缺失实验先进入本次 run 的 `microbench_candidates/`。只有
应用无关、参数化、冷启动可复现且通过机制门禁的粒子，才由现有 promotion
流程追加到 `microbench/`。人工报告引用自然语言名称；内部 ID 只留在
开发者附录，因此积累不会污染人类语义。

# RTX 5090 整模瓶颈矩阵（Qwen3.5-0.8B GPTQ）

结论：`lm_head` 是 GPU 活跃区间里的最大 kernel，但不是整段推理墙钟里的绝对主导项。此前一直继续看它，既有真实的 profiler 依据，也存在“已经做出成果后继续深挖”的路径依赖。对当前 SM120 合同，这条路线现已关闭。

| B=1，6 个自然请求，各生成 64 token | 736.437 ms | 146.869 ms（19.94% 墙钟） | 83.5% | 约 5.6% | `lm_head` 算子 1.3421x 仅对应 1.0444x Amdahl 上限；实测整模 pooled 1.0058x、保守 0.9871x，关闭 |
| B=8，并发生成 64 token | 159.209 ms | 30.278 ms（19.02% 墙钟） | 66.9% | 约 17.6% | 即使 Marlin 假设 2x，整模上限也只有 1.0170x，未过 1.02x 门槛 |

`cudaEventSynchronize` 在 B=1 为 775 次、API 累计 308.083 ms，在 B=8 为 132 次、62.676 ms。这不等于有同样多的 CPU 开销可以直接删除：同步调用包含等待 GPU 的时间，且部分事件承担输入准备和输出生命周期正确性。它说明下一步应当定位“哪些等待暴露在关键路径上”，而不是直接删除同步。

## 新的选题规则

1. 每个候选先在目标 workload 上测出组件墙钟占比。
2. 用 `1 / ((1-share) + share/component_speedup)` 算整模乐观上限。
3. 上限低于 1.02x，停止编码并记录重开条件。
4. 上限通过后，仍需 paired 整模实测；算子 benchmark 不能代替整模结果。
5. B=1 decode、并发 decode、prefill 分开建合同，不把一个场景的排名外推给另一个场景。

下一优先级是对每 token 的 host/control/synchronization 暴露时间做因果归因。只有归因后算出的整模上限达到 1.02x，才进入实现阶段。
